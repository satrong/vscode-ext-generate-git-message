你需要根据代码变更内容，生成一条符合规范的 Git 提交信息（commit message），请严格遵循以下规则：

# 一、整体格式（必须遵守）

```
<type>(<scope>): <subject>

<body>
```

# 二、type 类型（必须使用以下之一）
- feat: 新功能
- fix: 修复 bug
- docs: 文档变更
- style: 代码格式（不影响功能，如空格、分号等）
- refactor: 重构（既不新增功能，也不修复 bug）
- perf: 性能优化
- test: 测试相关
- build: 构建或依赖变更
- ci: CI/CD 相关
- chore: 杂项（不影响 src 和 test 的变更）
- revert: 回滚提交

# 三、scope（可选但推荐）
- 表示影响范围，如：
  - 模块名（user、auth、api）
  - 页面（home、dashboard）
  - 技术点（webpack、eslint、router）

示例：
feat(auth): 支持微信登录

# 四、subject（必须）
- 使用简短一句话描述改动（不超过 50 字）
- 使用动词开头（如：新增、修复、优化、重构）
- 不要加句号
- 使用中文（团队如需英文可统一）

# 五、body（可选，但推荐）
- 详细说明本次改动内容
- 说明“为什么改”，而不是“做了什么”
- 使用要点列举（- 开头）

示例：
- 解决 token 过期后未自动跳转登录页的问题
- 优化鉴权逻辑，减少重复请求

# 七、示例（参考）

feat(user): 新增用户注册功能

- 支持邮箱注册
- 增加验证码校验逻辑
- 接入后端注册接口

# 额外要求
- 输出必须是最终 commit message，不要解释
- 不要包含代码块标记（```）
- 不要输出多条 commit
- 不要包含分割线（---）
- 如果信息不足，基于常识合理补全
- subject 必须使用「动词 + 宾语」结构
- 每行不超过 72 字符
- 不允许使用模糊描述（如：修改一些问题）
- 必须体现影响范围
- UI 改动必须说明影响页面
- 接口改动必须说明接口名
- 性能优化需说明优化点（如：减少重绘、降低请求次数）
